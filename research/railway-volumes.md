# Railway persistent volumes and media-file workflow

Issue: [#18 — Researching Railway volumes and media-file workflows](https://github.com/BalaStic/waczak-tv/issues/18)

**Documentation checked:** 2026-11-19. This report uses Railway's official documentation only. Application-specific consequences below use the issue's supplied context (single-service Node app, local media folders, startup playlist snapshot, and playback checkpoints); no application files or media were inspected.

## Recommendation

Use one Railway volume for both media and playback checkpoints, mounted at the app's expected absolute data directory. Populate or refresh media manually using Railway's volume file CLI (`railway volume browse` or `railway volume files upload`) or SFTP/SCP into the mounted directory. A service restart/redeploy is necessary for the app to rebuild a playlist that is snapshotted only at startup. Keep volume backups and capacity headroom in the operational plan. Do not rely on a build or pre-deploy step to seed the volume.

## Mount path and app layout

Railway makes a volume available as a read/write directory at its configured mount path; for example, a volume mounted at `/foobar` is accessed at `/foobar`. If the app writes to a relative directory such as `./data` and its app directory is `/app`, mount at `/app/data` so those writes reach persistent storage. Railway provides `RAILWAY_VOLUME_NAME` and `RAILWAY_VOLUME_MOUNT_PATH` at runtime. [Railway: Using Volumes](https://docs.railway.com/volumes)

The volume is mounted when the service container starts, not during image build or a pre-deploy command. Files copied into a matching path at build time do not thereby get written to the mounted volume; pre-deploy commands cannot access the volume either. Railway says volumes are not mounted as overlays. [Railway: Using Volumes](https://docs.railway.com/volumes)

A service can have only one volume, and replicas cannot be used with volumes. The app should therefore put media and checkpoint data under the one mounted directory (or otherwise make sure all required persistent data fits in that volume). Volumes mount as root; if the container runs as a non-root user and has permission problems, Railway documents `RAILWAY_RUN_UID=0` as the setting to use. [Railway: Volumes reference](https://docs.railway.com/volumes/reference); [Railway: Using Volumes](https://docs.railway.com/volumes)

## Lifecycle and persistence

Railway documents volumes as persistent data storage, in contrast to deployment-local ephemeral storage, and explicitly recommends a volume when data must persist between deployments. Thus files and checkpoints written under the mount path persist across ordinary deploy/redeploy cycles. A process restart also does not replace the attached volume; however, application-level flushing and consistency are separate concerns. [Railway: Using Volumes](https://docs.railway.com/volumes); [Railway: Deployments reference](https://docs.railway.com/deployments/reference)

Railway prevents two deployments from simultaneously mounting a service's volume to avoid data corruption. A redeploy with a volume therefore has a small downtime window, even if a healthcheck is configured. Separately, Railway's deployment documentation says the previous deployment receives SIGTERM after its replacement is online and is given **0 seconds by default** before SIGKILL; `RAILWAY_DEPLOYMENT_DRAINING_SECONDS` controls the grace period. Set a suitable draining interval and have the app flush checkpoints on shutdown, but do not assume that shutdown flushing is guaranteed with the default. Railway can also initiate mandatory service redeployments for host migrations and platform updates. [Railway: Volumes reference](https://docs.railway.com/volumes/reference); [Railway: Deployments reference](https://docs.railway.com/deployments/reference)

For this app, put the checkpoint directory on the volume; otherwise deployment-local checkpoint files are not covered by the volume's persistence guarantee. Since media is snapshotted into a playlist at startup, a manual upload made while the process is running changes the files on disk but not the already-created in-memory playlist (inference from the stated app behavior). Restart/redeploy after a media refresh so startup can rescan and snapshot the new playlist. Plan for the volume-backed redeploy's downtime. A checkpoint that has not been flushed before a hard stop can still be lost; the Railway docs do not promise application-level write durability or checkpoint consistency.

## Region, capacity, and backup/restore constraints

A volume follows the region of its attached service. Creating a volume attaches it in the service's region. Changing the service's region, or attaching a detached volume in another region, requires volume migration; Railway warns migration may take a while and causes service downtime. Choose the intended service region before loading a large media library. [Railway: Regions](https://docs.railway.com/deployments/regions)

Published default volume capacities are 0.5 GB on Free/Trial, 5 GB on Hobby, and 50 GB on Pro. Paid plans support resizing; Railway documents live resize without downtime, but says some cases (for example, reaching 100% capacity) require an offline resize that restarts the service. Downsizing is unsupported. Size for media, checkpoints, and working headroom rather than filling the volume. [Railway: Volumes reference](https://docs.railway.com/volumes/reference); [Railway: Using Volumes](https://docs.railway.com/volumes)

Railway supports manual volume backups and daily, weekly, or monthly schedules. Scheduled retention is 6 days for daily, 27 days for weekly, and 89 days for monthly. Manual backups are limited to 50% of the volume's total size. Restoring a backup stages a replacement volume at the same mount path; review and deploy the staged change to apply it. The prior volume remains in the project, unmounted. The restored volume carries backups up to and including the restored backup; newer backups remain on the old volume. Backups can only be restored into the same project and environment, and wiping a volume deletes its backups. Railway labels volume backups a newer feature still under development. The docs do not state whether a backup taken during active writes is application-consistent. [Railway: Backups](https://docs.railway.com/volumes/backups)

## Supported file population and refresh options

- **Railway volume CLI:** `railway volume browse /` opens the interactive file browser, which can browse, upload, download, edit, rename, and delete files. Non-interactive `railway volume files` commands support listing, uploading, downloading, renaming, and deleting. Upload accepts a file or directory and supports `--overwrite`; see the CLI reference for exact arguments and volume selection. This is the most direct documented workflow for manual media management. [Railway: Using Volumes](https://docs.railway.com/volumes); [Railway CLI: `railway volume`](https://docs.railway.com/cli/volume)
- **Railway SSH with SCP/SFTP:** `railway ssh` opens a shell in a deployed service container. Railway's SSH endpoint supports SFTP, so system `scp` and `sftp` can transfer files into or out of a running container, including its mounted volume. Use the actual mounted directory as the transfer destination. SSH requires a key registered with Railway; the service domain or service instance ID is the SSH username. [Railway CLI: `railway ssh`](https://docs.railway.com/cli/ssh); [Railway: Volumes reference](https://docs.railway.com/volumes/reference)
- **Railway Buckets (different storage model):** Buckets are private S3-compatible object storage, separate from block volumes. They can be accessed via the S3 API and the docs describe file upload/serving options, but Railway documents no native bucket-to-volume sync. Using a bucket as the media source would require the app or an operational process to use S3 rather than assume local files. Buckets currently have no automatic backups or snapshots. [Railway: Storage Buckets](https://docs.railway.com/storage-buckets); [Railway: Uploading & Serving Files](https://docs.railway.com/storage-buckets/uploading-serving)

The Railway volume docs do not describe seeding a volume during build or pre-deploy; they explicitly say it is not mounted at those stages. For the stated manual-management plan, use the volume CLI or SSH/SFTP/SCP after the service and volume are provisioned, and restart/redeploy after uploads when the startup playlist snapshot must be refreshed.
