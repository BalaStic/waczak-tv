# Browser playback options for a shared live MP4 channel

**Context:** Research requested by [ticket](../tickets/research-browser-playback-options.md) for the [Wayfinder map](../map.md). Findings checked 2026-10-15. Scope is the map's Windows-only, manually launched local webapp and local viewers; LAN access is out of scope.

## Finding in brief

For this fixed, locally stored playlist, use ordinary HTML `<video>` playback of each MP4 over HTTP, plus a small authoritative server-side playlist clock/state endpoint. Prefer H.264/AVC video in a conventional MP4 file; for maximum compatibility, use AAC-LC audio if an audio track exists (and keep the element muted). Implement byte-range responses so browsers can seek/restart efficiently. Give every viewer a snapshot of the authoritative item and playhead, then reconcile on updates. This is materially simpler than transcoding/packaging a live segmented stream or publishing WebRTC media, and it fits a playlist whose source files already exist on disk.

This is not frame-locked synchronization: browsers fetch, buffer, decode, schedule, and may stall independently. Treat a shared position as a server-authoritative target and correct drift, not as proof that all displays show the same frame at the same instant.

## Browser, MP4 and codec constraints

An `.mp4` extension identifies a container, not the codecs inside it. MP4 can carry different video/audio codecs and profiles; the container's MIME type alone does not establish that a particular decoder can play the tracks. The interoperable target is H.264/AVC video (`avc1`) in MP4, with AAC-LC (`mp4a.40.2`) if audio is present. The codec string can identify a specific profile/level; `canPlayType()` can be used as an early signal, but must not replace a playback/error check on the actual file. [MDN: codecs in common media types](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/codecs_parameter), [HTML Standard: media type support](https://html.spec.whatwg.org/multipage/media.html#mime-types).

[Microsoft Edge video playback troubleshooting](https://learn.microsoft.com/en-us/troubleshoot/microsoft-edge/development/video-playback-issues) | MP4/H.264 is the safe target; do not assume HEVC or another codec merely because the filename ends in `.mp4`. Hardware acceleration is hardware/driver dependent, not a format guarantee. |

Microsoft documents native Windows Media Foundation support for MPEG-4/H.264 and MP4 containers, but optional Windows components and the chosen codec/profile still matter. [Microsoft: MPEG-4 support in Media Foundation](https://learn.microsoft.com/en-us/windows/win32/medfound/mpeg-4-support-in-media-foundation), [supported media formats](https://learn.microsoft.com/en-us/windows/win32/medfound/supported-media-formats-in-media-foundation). Consequently, inspect/probe actual files or validate playback and report unsupported files; do not treat extension-based scanning as proof that the file is playable. A lightweight browser-side `canPlayType('video/mp4; codecs="avc1..., mp4a.40.2"')` is advisory; actual `error`/`play()` outcomes are more decisive.

For fully silent media, no audio track is necessary. If tracks are retained, set the video element muted before asking it to play: Chrome explicitly allows muted autoplay, but Firefox's site/user autoplay setting can block even muted video, and Edge documents autoplay policy as a playback issue. Handle `play()` rejection and provide a one-time user-gesture fallback instead of assuming autoplay succeeds. [Chrome autoplay policy](https://developer.chrome.com/blog/autoplay/), [Firefox autoplay settings](https://support.mozilla.org/en-US/kb/block-autoplay), [HTML Standard: `play()`](https://html.spec.whatwg.org/multipage/media.html#dom-media-play).

## HTTP delivery and seeking

Serve files as `video/mp4` over the local HTTP origin rather than relying on a `file://` media URL. A file URL has no server-side channel state shared among viewers; HTTP provides the common application origin and state service. The media element can fetch and play an ordinary file resource directly; no MSE player is needed for a static MP4. [HTML Standard: video element](https://html.spec.whatwg.org/multipage/media.html#the-video-element).

Implement HTTP byte ranges for media URLs. A media client can ask for part of a file (for example, after a seek or when resuming); a server fulfilling that request returns `206 Partial Content` and a correct `Content-Range`, as defined by [RFC 9110 §14 and §15.3.7](https://www.rfc-editor.org/rfc/rfc9110.html#section-14). Range support enables efficient seeking/resume and targeted reads rather than forcing a start-at-zero transfer; it is especially important for late joiners seeking into a large MP4. Verify with a real `Range: bytes=...` request and an in-browser seek. If the server ignores Range and returns `200` with the full file, the browser cannot receive the requested partial response. MDN's [media delivery guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Audio_and_video_delivery) covers serving media and range requests.

Each viewer still has its own media element and media requests. With direct files, each open viewer independently reads/downloads and decodes the relevant bytes; the state channel should carry only compact control state, not video frames. Increasing viewer count therefore increases file I/O and local network-stack work, even though this is a single host rather than internet egress. A `moov` index at the end of an MP4 can also delay initial metadata discovery; where files are prepared in advance, placing the index at the front (`faststart`) improves progressive startup. [FFmpeg MOV/MP4 muxer options](https://ffmpeg.org/ffmpeg-formats.html#MOV_002fMP4_002fISMV).

## Shared position, late joins and multiple viewers

The `<video>` element exposes `currentTime` (read/write) for the local playhead, and `duration` for media length. Seeking is asynchronous; duration may be unknown until metadata loads, and playback/buffering events are local to that element. [WHATWG media elements: `currentTime`, duration, seeking and events](https://html.spec.whatwg.org/multipage/media.html#media-elements), [MDN: `loadedmetadata`](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/loadedmetadata_event).

A reliable shared-live model therefore needs a single server-side schedule/state authority, not a separate “play next when this browser's `ended` fires” rule in every viewer. Store a playlist revision/order, current item ID, and either (a) an absolute item start timestamp plus duration, or (b) a position plus the time that position was sampled. A late join first requests the full current snapshot and computes the current offset from it; WebSocket/SSE/poll updates can carry later transitions/corrections. The snapshot is essential: a new viewer cannot depend on having received an earlier transition event. WebSocket is one standard way for the server and clients to exchange live state in both directions, but is not needed for the video bytes. [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html).

On load, wait for `loadedmetadata`/seekability before applying a target `currentTime`; then call `play()` and handle failure. Periodically compare local playhead with the server target, and correct meaningful drift by seeking (or very gently varying rate if that is an explicit product choice). A seek is not instantaneous and may wait for range data. If a browser stalls or a tab is suspended, that client can visibly fall behind; resynchronize it on recovery/visibility and after receiving state. The HTML media standard exposes these controls/events, but does not create cross-browser shared playback synchronization. A practical MVP should aim for approximate alignment with bounded drift and a clear recovery path, not sample-accurate lockstep.

For a fixed alphabetical loop, the scheduler needs reliable durations to compute which item and offset apply at any time. In-page `duration` is `NaN` until media metadata exists; server-side preflight/probing or a startup metadata pass is needed if the server must determine a late join's location without relying on a viewer having already loaded all preceding media. At transitions, advance the authoritative state once, persist/broadcast the new item and anchor, then let clients load/seek to that state. Do not let a single client's `ended` or `error` event advance/skip globally: it may be delayed by a local stall or indicate that only that browser/Windows installation lacks a decoder. Instead, report the client failure and use a server-side preflight policy or a defined consensus/timeout rule before changing shared state. [HTML Standard: duration, `ended` and `error`](https://html.spec.whatwg.org/multipage/media.html#media-elements).

On restart, persist the ordered playlist identity/revision and a position anchor (item + offset + saved-at time, or a schedule start time). Decide explicitly whether downtime freezes the channel at the saved position or the channel clock continues through downtime; both are implementable, but they yield different restart states. Rebuild the anchor from persisted state at process startup and provide that same snapshot to every client. If file membership/order changes, a playlist revision makes it possible to detect that saved index/durations no longer describe the same schedule.

## Viable approaches compared

| Approach | Strengths | Costs / constraints | Fit for this ticket |
|---|---|---|---|
| **A. Progressive HTTP MP4 per file + HTML `<video>` + server clock/state** | Native browser demux/decode; simplest path from existing files; range-seeking works; late join is a state lookup plus seek; independent of a real-time encoder. | Requires a correct range-capable file server and custom state/synchronization; every viewer requests/decodes its own copy; transition gaps and drift are possible. | **Recommended MVP.** |
| **B. Pre-concatenate/normalize the playlist into one MP4** | One media URL and no per-file source swap; can reduce gaps between files; late join can seek within the long resource. | Playlist changes require rebuilding output; stream-copy concatenation requires compatible streams/parameters, while inconsistent sources require remux/transcode; each viewer still requests its own bytes; schedule and restart state remain application concerns. [FFmpeg concat demuxer](https://ffmpeg.org/ffmpeg-formats.html#concat). | Viable if the library is stable and seamless transitions outweigh rebuild/normalization work; not necessary for the first MVP. |
| **C. Segment packaging with HLS/DASH via Media Source Extensions** | Segment boundaries/manifests support live windows, adaptation and more controlled buffering; MSE lets JavaScript append media segments to a media element. [W3C MSE](https://www.w3.org/TR/media-source-2/). | Requires segmenting/manifest generation, a compatible player pipeline, and explicit timestamp/discontinuity handling; significantly more moving parts than serving existing files. | Use only if adaptive bitrate, rolling DVR/live-window behavior, or more advanced segment-based recovery becomes a requirement. |
| **D. Real-time WebRTC broadcast** | Designed for interactive, real-time media transport; can be attractive for low-latency broadcast and coordinated real-time streams. [W3C WebRTC](https://www.w3.org/TR/webrtc/). | A file playlist must still be fed/encoded into a live media source; multi-viewer distribution needs server-side fan-out/relay design and reconnection/late-join semantics. It is not a direct replacement for range-served MP4 files. | Overkill for local playback of a static folder; revisit only if near-live latency and tighter playback coordination become dominant requirements. |

A single generated/looping HTTP media stream is another option, but it does not automatically provide instant late-join access: the server must retain a seekable/DVR window and support ranges, or use segments. None of these delivery options removes the need to define who owns playlist position, what “resume” means, or how an individual client's decoder/buffer failure affects the shared schedule.

## Windows-local hosting constraints

- Bind the server explicitly to loopback (`127.0.0.1`, and/or `::1`) rather than all interfaces if LAN access is intentionally out of scope. Winsock's `bind` associates the socket with a local address; use the actual loopback address and verify the bound endpoint. [Microsoft Winsock `bind`](https://learn.microsoft.com/en-us/windows/win32/api/winsock/nf-winsock-bind), [RFC 1122 §3.2.1.3](https://www.rfc-editor.org/rfc/rfc1122.html#section-3.2.1.3). This limits reachability to the host's loopback path; it is not an authorization barrier against other local processes.
- Serve the page, state endpoint and media under one stable `http://localhost:<port>` origin. Loopback/localhost is considered potentially trustworthy by the Secure Contexts standard, even without HTTPS, which is useful if a secure-context-only API is later needed. [W3C Secure Contexts](https://www.w3.org/TR/secure-contexts/), [MDN secure contexts](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts).
- Keep browser page and media/control endpoints same-origin. Microsoft documents Edge Local Network Access restrictions and a loopback allowlist policy for requests to `localhost`, `127.0.0.1`, and `::1` (policy supported from Edge 146). Avoid designing around a public/remote-origin page that reaches into localhost; test the actual packaged URL in current Edge and Chrome. [Microsoft Edge `LoopbackNetworkAllowedForUrls`](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-policies/loopbacknetworkallowedforurls).
- A manually launched server needs a deterministic startup URL and port policy. A fixed port is easy to bookmark but can be occupied; an ephemeral port avoids collisions but must be surfaced to the launcher/browser. Startup should fail clearly or report the chosen address, not silently expose a listener on LAN interfaces.
- Localhost HTTP works for this local-only scope, but it does not encrypt local traffic or prevent another local process from requesting media/state. Do not describe loopback binding as authentication or protection from local malware.

## Recommended MVP boundary

1. Scan/probe the configured files, define the stable alphabetical order and durations, and record which files failed preflight.
2. Serve normal MP4 files through a same-origin `video/mp4` route that honors byte ranges.
3. Keep one authoritative channel schedule/anchor in the host process and persist enough information for an explicit restart policy.
4. Give each viewer a snapshot on connect, apply the target item/position after metadata is ready, and periodically reconcile meaningful drift; use small state messages only.
5. Start muted and handle autoplay rejection (including Firefox/user-policy cases); surface a manual start affordance and per-client playback error.
6. Bind only to loopback; verify current Edge, Chrome and Firefox with representative files, a late join, a multi-viewer run, a range seek, a file transition, and both restart policies.
